# INC-003 · Vytvorenie účtu hlási „Unexpected server error“, ale účet existuje

[← INC-002](INC-002.md) · [Podporný balík](../README.md) · [Prevádzková príručka](../runbook.md)

| | |
|---|---|
| **Typ** | Incident rekonštruovaný zo skutočného defektu |
| **Služba** | Wallet API — `POST /api/auth/register` |
| **Priorita** | **P3** — stredný dopad × stredná naliehavosť |
| **Stav** | Vyriešený, uzavretý |
| **Prepojený problém** | BUG-016 v [`log/BUGS.md`](../../../log/BUGS.md) — súbežné registrácie rovnakého e-mailu vracajú 500 |

Nikto tento incident nenahlásil; našla ho sonda. Ticket je napísaný tak, ako by sa riešil, keby sa s ním niekto stretol.

<a id="reported-symptom"></a>
## Hlásený príznak

Ako by to človek povedal: *„Zaregistroval som sa a dostal chybu. Keď som to skúsil znova, e-mail už bol zaregistrovaný.“* Obvykle k tomu vedie dvojité ťuknutie na tlačidlo alebo odoslanie formulára z dvoch kariet.

<a id="impact-and-urgency"></a>
## Dopad a naliehavosť

- **Dopad: stredný.** Jednému človeku pri prvom kontakte s aplikáciou hlási zlyhanie niečoho, čo nezlyhalo. Údaje sú správne: presne jeden účet.
- **Naliehavosť: stredná.** Prihlásenie funguje okamžite.

<a id="timeline"></a>
## Časová os

| Kedy | Čo |
|---|---|
| S21 | Sonda odoslala päť párov súčasných registrácií rovnakej novej adresy: všetkých päť párov odpovedalo 201 a 500, v serverovom logu `SQLITE_CONSTRAINT_UNIQUE` |
| 2026-09-27 | Vyriešenie v `e291ea9`: odmietnutie unique indexom sa zmenilo na rovnaké 409 ako kontrola duplicity. Regresia: race scenár E, 120 párov, každý s jedným 201 a jedným 409 |
| 2026-09-27 | Reprodukcia správania pred opravou pre tento ticket. Riadky nižšie sú z tohto behu |

**O dôkazoch.** Reprodukcia prebehla na dočasnej kópii vtedajšieho aktuálneho kódu bez mapovania pridaného opravou — troch riadkov v `src/auth.js`, ktoré menia `SQLITE_CONSTRAINT_UNIQUE` na 409 — a odoslala päť párov súbežných registrácií. Riadok `UNHANDLED` je bez zásobníka volaní obsahujúceho názvy priečinkov počítača; namiesto neho je uvedený prvý rámec aplikácie.

<a id="diagnosis"></a>
## Diagnostika

1. **Od referencie k riadkom** (`4edc1414`):

   ```text
   {"time":"2026-09-27T11:38:11.318Z","level":"error","event":"UNHANDLED","request_id":"4edc1414-31ab-479c-8741-bea657e6bcdd","method":"POST","route":"/api/auth/register","code":"SQLITE_CONSTRAINT_UNIQUE","message":"UNIQUE constraint failed: users.email"}
     first frame in the app: at src/auth.js:83:8
   {"time":"2026-09-27T11:38:11.328Z","level":"info","event":"request","request_id":"4edc1414-31ab-479c-8741-bea657e6bcdd","method":"POST","route":"/api/auth/register","status":500,"duration_ms":76.5,"user_id":null}
   ```

2. **Prečítať trvanie.** 76.5 ms zodpovedá približne jednému hashu hesla: požiadavka prešla kontrolou „už zaregistrovaný?“, zahashovala heslo a až potom našla obsadenú adresu. Nebola to teda oneskorená duplicita, ale jedna z dvoch súčasných požiadaviek.
3. **Skontrolovať uložené údaje** cez [Q0](../sql-diagnostics.md#q0--find-a-persons-user-id):

   ```text
   Q0 user-id for that address: [{"user_id":1,"created_at":"2026-09-27 11:38:11"}]
   ```

   Jeden účet, nie dva ani napoly vytvorený. Nesprávna bola len chyba v odpovedi.
4. **Celý beh:**

   ```text
   BUG-016 BEFORE (fix reverted in a temporary copy): 5 × 201 · 500
   ```

<a id="root-cause"></a>
## Koreňová príčina

Registrácia najprv overila obsadenosť adresy, potom zahashovala heslo a vložila účet. Hashovanie je asynchrónne, preto obe registrácie tej istej adresy prešli kontrolou pred prvým vložením. Druhý insert narazil na unique index databázy a nič túto chybu nepreložilo; generický handler ju vrátil ako 500.

<a id="workaround"></a>
## Náhradný postup

Prihlásiť sa rovnakým e-mailom a heslom: účet existuje. Ak pokusy použili odlišné heslá, napríklad z dvoch kariet, uložené je heslo toho, ktorý skončil prvý; ak prvé nefunguje, skúsiť druhé.

<a id="resolution"></a>
## Vyriešenie

`e291ea9`. Unique index je jediná kontrola, ktorá platí pri súbehu, preto sa jeho odmietnutie teraz mapuje na rovnaké 409 ako kontrola duplicity. Účet a úvodné kategórie sa zapisujú v jednej transakcii, aby prerušenie registrácie nezanechalo účet bez kategórií. Na commitnutom kóde rovnakých päť párov dalo:

```text
BUG-016 AFTER (the code as committed): 5 × 201 · 409
```

<a id="incident-or-problem"></a>
## Incident alebo problém

**Incidentom** bolo hlásenie „unexpected server error“ človeku, ktorému sa účet v skutočnosti vytvoril; prihlásenie mu problém vyriešilo. **Problémom** BUG-016 bolo hlásenie súbehu už chráneného databázou ako zlyhania aplikácie. Opravilo ho preloženie odpovede databázy, nie pokus zabrániť súbehu.
