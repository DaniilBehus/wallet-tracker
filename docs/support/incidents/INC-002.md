No person reported this; it was found by a load test. This ticket is written
the way it would have been handled had somebody met it.

## Reported symptom

How a person would put it: *"Everything is frozen. Even opening the month takes
ages, and then it suddenly works again."* The person reporting it is not the one
causing it.

## Impact and urgency

- **Impact: High.** Every request from every person, the health check
  included, waits while the burst lasts. Causing it needs no account: wrong
  passwords for any address will do.
- **Urgency: High.** The people affected have no workaround, and it lasts as
  long as whoever sends the passwords keeps going.

**About the evidence.** The reproduction ran on a temporary copy of today's code
with only the second fix reverted — `await bcrypt.compare(…)` back to
`bcrypt.compareSync(…)` in `src/auth.js` — and the limiter set out of reach
(`LOGIN_MAX_FAILURES=1000000`), as the original measurement of allowed logins
did. Twenty connections sent wrong passwords for five seconds while the health
check was timed from outside, ten times a second.

## Diagnosis

1. **Time a request from outside.** The health check took **1059.5 ms** to
   answer. Its own log line says something else:

   ```text
   {"time":"2026-09-27T11:39:38.383Z","level":"info","event":"request","request_id":"3ccb7142-21b9-4941-b971-f5f0db1eea99","method":"GET","route":"/api/health","status":200,"duration_ms":0.2,"user_id":null}
   ```

   `duration_ms` is 0.2. The second the person waited was spent before the
   request reached the app's code, while the process was busy with something
   else. **The request log measures time inside the app, so a stalled process is
   invisible in the lines of the requests it stalls.** This is why the runbook
   tells you to time from outside when "everything is slow".
2. **Find what the process was busy with.** The lines answered just before that
   health check are logins, one every ~52 ms, each taking ~52 ms. That is one
   password check at a time, with nothing else answered in between:

   The run as a whole:

   ```text
   BEFORE (fix reverted in a temporary copy): 114 wrong-password logins in 5 s (114 × 401); health polled 4×: p50 1043.8 ms, p95 1059.5 ms, max 1059.5 ms
   ```

   Four health checks in five seconds, where forty were due: each one waited
   its turn behind the hashing.
3. **The database has nothing to add.** The cause was CPU time on the one
   thread that serves requests, and the login counters are kept in memory. No
   query applies, and saying so is part of the diagnosis: the obvious place to
   look was the wrong one.

## Root cause

Checking a password with bcrypt at cost 10 takes about 50 ms, and the synchronous
call did that on the event loop — the only thread that answers requests. While
it ran, nothing else could be served. Twenty attempts a second is a full second
of hashing every second, so everything else queued behind it.

## Workaround

For the people affected, none at the time. For an operator, stopping the
source of the attempts. A restart would not have helped: the burst resumes
against the new process.

## Resolution

Two changes, both in place:

1. **The limiter** (D-016) refuses a sixth failed attempt within 15 minutes,
   counted per e-mail and per network address, before the password is checked.
   A burst costs five checks and then only cheap 429s.
2. **Hashing off the event loop** (S12): `bcrypt.compare` and `bcrypt.hash` run
   on the thread pool, so a check occupies a worker, not the process.

On the committed code the same burst, with the limiter again out of reach so
that every attempt is really checked, gave:

```text
AFTER (the code as committed): 385 wrong-password logins in 5 s (385 × 401); health polled 41×: p50 0.9 ms, p95 1.2 ms, max 1.8 ms
```

The logins now overlap — each takes longer (~270 ms) because twenty share the
pool's workers, but they finish a few milliseconds apart and never hold the
process:

Regression cover: the k6 scenarios TC-LOAD-002 and TC-LOAD-003, and the API

## Incident or problem

The **incident** was the stall everyone felt; it ended when the burst ended,
with nothing support could do to shorten it. The **problem**, BUG-004, was why
one kind of request could hold all the others, and it took two changes to
close: the limiter bounded how often the cost could be paid, and moving the hash
off the event loop removed the cost from everyone else's requests.
