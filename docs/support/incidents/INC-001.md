## Reported symptom

How a person would put it: *"I changed the amount of my loan and it said
something went wrong. I tried again and it worked."*

## Impact and urgency

- **Impact: Medium.** Only a deployment running two app processes on one
  database file. There, an edit arriving at the same moment as a payment from
  the other process failed in about one pair in eight to ten. Nothing was lost.
- **Urgency: Medium.** Repeating the edit worked, and nothing was left half
  written.

The defect register rates BUG-012 **P1**, because the specification says a 500
must never be reachable. Both are right: the problem's priority measures the
broken promise, the incident's measures what a person loses.

**About the evidence.** Request ids did not exist when the defect was found. The
reproduction ran on a temporary copy of today's code with only the fix reverted
— `pay.immediate()` and `edit.immediate()` back to `pay()` and `edit()` in
`src/routes/schedules.js` — two server processes on one database, 40 pairs of a
payment on one and an edit on the other. The `UNHANDLED` line is shown without
its stack, which holds the machine's folder names; the first frame inside the
app is given instead.

## Diagnosis

1. **From the reference to the lines.** The person's reference, `de37fd55`,
   found two lines in the log of the process that answered:

   ```text
   {"time":"2026-09-27T11:38:38.676Z","level":"error","event":"UNHANDLED","request_id":"de37fd55-7224-427b-b684-7ac652ceadef","method":"PATCH","route":"/api/schedules/:id","code":"SQLITE_BUSY","message":"database is locked"}
     first frame in the app: at src/routes/schedules.js:216:8
   {"time":"2026-09-27T11:38:38.676Z","level":"info","event":"request","request_id":"de37fd55-7224-427b-b684-7ac652ceadef","method":"PATCH","route":"/api/schedules/:id","status":500,"duration_ms":1.4,"user_id":1}
   ```

2. **Read the duration.** `SQLITE_BUSY` usually means something held the lock
   and time ran out, but the busy timeout is 5 seconds and this request was
   refused in **1.4 ms**. Nothing waited. A refusal that does not wait is SQLite
   declining to upgrade a lock, not a lock held too long, so a longer timeout
   would change nothing.
3. **Look at the other process.** The payment of the same pair, sent to the
   other process at the same moment, answered 200. Across the run:

   ```text
   BEFORE (fix reverted in a temporary copy): 35 × pay 200 · edit 200, 5 × pay 200 · edit 500
   ```

4. **Check nothing was half written** with [Q3](../sql-diagnostics.md#q3--scheduled-payments-presses-of-pay-against-the-expenses-they-wrote):

   ```text
   [{"schedule_id":1,"name":"Race loan","total_count":1200,"paid_count":40,"active":1,"linked_expenses":40,"unlinked_payments":0}]
   ```

   Forty payments, forty expenses: every payment landed whole, and every failed
   edit rolled back.

## Root cause

A plain `BEGIN` starts a *deferred* transaction. It reads under a shared lock
and asks for the write lock at its first write. If the other process has
written in between, what this transaction read is out of date, so SQLite
refuses the upgrade at once with `SQLITE_BUSY`, and `busy_timeout` does not
apply to that refusal. The edit read the loan, the payment on the other process
wrote to it, and the edit could then not write. One process alone never meets
this: better-sqlite3 is synchronous, so its handlers never interleave.

## Workaround

Repeat the edit: by then the payment has finished and nothing is in the way.
For an operator: run one app process per database file.

## Resolution

`pay.immediate()` and `edit.immediate()`: `BEGIN IMMEDIATE` takes the write lock
before reading, so there is no upgrade to refuse, and a second writer waits for
that lock under the busy timeout instead of failing. The rule, D-030: a handler
that reads a row, decides from it and writes does all three inside one
`.immediate()` transaction. `qa/race/` scenario C runs two processes on one
database every time; on the committed code the same reproduction gave:

```text
AFTER (the code as committed): 40 × pay 200 · edit 200
```

## Incident or problem

The **incident** was the failed edit a person saw, and the retry restored their
service. The **problem**, BUG-012, was why it could happen at all, and it
needed a change to the code. Closing the incident with a workaround did not
close the problem; the change did.
