No person reported this; it was found by a probe. This ticket is written the
way it would have been handled had somebody met it.

## Reported symptom

How a person would put it: *"I signed up and got an error. When I tried again it
said my e-mail is already registered."* The usual way to get there is a double
tap on the button, or the form submitted from two tabs.

## Impact and urgency

- **Impact: Medium.** One person, at their first contact with the app, is told
  something failed that did not. The data is right: exactly one account.
- **Urgency: Medium.** Signing in works straight away.

**About the evidence.** The reproduction ran on a temporary copy of today's code
with only the fix's mapping removed — the three lines in `src/auth.js` that turn
`SQLITE_CONSTRAINT_UNIQUE` into a 409 — and sent five pairs of simultaneous
registrations. The `UNHANDLED` line is shown without its stack, which holds the
machine's folder names; the first frame inside the app is given instead.

## Diagnosis

1. **From the reference to the lines** (`4edc1414`):

   ```text
   {"time":"2026-09-27T11:38:11.318Z","level":"error","event":"UNHANDLED","request_id":"4edc1414-31ab-479c-8741-bea657e6bcdd","method":"POST","route":"/api/auth/register","code":"SQLITE_CONSTRAINT_UNIQUE","message":"UNIQUE constraint failed: users.email"}
     first frame in the app: at src/auth.js:83:8
   {"time":"2026-09-27T11:38:11.328Z","level":"info","event":"request","request_id":"4edc1414-31ab-479c-8741-bea657e6bcdd","method":"POST","route":"/api/auth/register","status":500,"duration_ms":76.5,"user_id":null}
   ```

2. **Read the duration.** 76.5 ms is about one password hash: this request got
   past the "already registered?" check, hashed the password, and only then
   found the address taken. So it was not a late duplicate. It was one of two
   requests running at the same time.
3. **Check what was stored** with [Q0](../sql-diagnostics.md#q0--find-a-persons-user-id):

   ```text
   Q0 user-id for that address: [{"user_id":1,"created_at":"2026-09-27 11:38:11"}]
   ```

   One account, not two and not a half-made one. The error was the only thing
   wrong.
4. **The run as a whole:**

   ```text
   BUG-016 BEFORE (fix reverted in a temporary copy): 5 × 201 · 500
   ```

## Root cause

Registration checked whether the address was taken, then hashed the password,
then inserted the account. Hashing is asynchronous, so two registrations of one
address both passed the check before either inserted. The second insert hit the
database's unique index, and nothing translated that error, so it reached the
generic handler as a 500.

## Workaround

Sign in with the same e-mail and password: the account exists. If the two
attempts used different passwords — two tabs, say — the one stored belongs to
whichever finished first, so try the other if the first is refused.

## Resolution

`e291ea9`. The unique index is the only check that holds under a race, so its
refusal is now translated into the same 409 the duplicate check gives. The
account and its starter categories are now written in one transaction, so an
interrupted registration cannot leave an account without categories. On the
committed code the same five pairs gave:

```text
BUG-016 AFTER (the code as committed): 5 × 201 · 409
```

## Incident or problem

The **incident** was one person told "unexpected server error" when their
account had in fact been made; signing in resolved it for them. The **problem**,
BUG-016, was that a race the database already guarded against was reported as
the app's own failure, and it was fixed by translating the database's answer
rather than by trying to prevent the race.
